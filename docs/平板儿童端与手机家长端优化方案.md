# 平板儿童端与手机家长端优化方案

> 2026-09-08 提案，尚未实施。目标：孩子在平板自然创作，家长在手机竖屏随时回看。复用现有 React、Express、家庭账号、作品、报告和周期摘要。

## 建议路线

先做“儿童平板体验 + 家长手机体验 + 可安装 PWA”，共用一套后端。当前不为两端各重写一套原生 App；原生绘画能力或应用商店分发产生明确需求后，再评估儿童端原生化或容器接入。

PWA 可提供桌面图标与独立窗口，仍允许链接直接访问。安装和通知能力随设备/浏览器变化，不能承诺所有国产平板、微信内置浏览器、Safari 都有相同体验。[MDN 安装说明](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)

## 当前最直接的问题

`frontend/src/app/App.tsx` 对非儿童页面启用 LandscapeGuard，窄屏竖向家长会被“请旋转屏幕”遮挡；当前家长侧更接近桌面工作台。应先移除家长/认证/官网的强制横屏，重新安排手机信息层次。

画布已有 Pointer Events 和会话草稿，但缺持久化离线草稿、可靠离线提交与实际平板触控验收。现有 analyze 将识别和保存放在同一次请求里，断网时不能当作云端已保存。

## 家长手机端

采用竖屏单列，底部四入口：概览、作品、报告、我的。把主题与沟通建议放入概览/作品详情，周报月报放入报告，避免七个横向标签争抢手机宽度。

首页依次呈现所选孩子、最新作品、简短观察、可操作的一条陪伴建议、最新周期摘要。详细依据折叠，图表避免需要横向滚动。作品点开为独立详情页，支持后退和直接链接；通知未来可直达该作品。

区分“有新作品”“解读处理中”“已有解读”“生成失败可重试”，没有报告时不显示空泛心理评分。底部操作适配设备安全区，关键触控目标建议至少 44×44 CSS px，设置与危险操作保持清楚的二次确认。

## 儿童平板端

保留 Nilo 和水彩空间，进入画布后收起大装饰，让画布占主要区域。横屏优先、竖屏和分屏仍可用；不把方向锁定作为功能前提。

工具栏适配手指和笔，提供左/右手布局、明显的撤销/橡皮/完成。采用稳定逻辑画布坐标和设备像素比绘制，旋转改变视口，避免缩放导致笔画形变。笔画可保存矢量操作加周期快照，减少频繁整图复制的成本。

Pointer Events 可区分 pen/touch/mouse 并提供设备支持的压力信息；先提供“手写笔模式忽略手指落笔”的控制，再在实际设备验证手掌误触，不能承诺 Web 能完全替代原生防误触。压力只能用于绘画笔触，不自动作为心理分析依据。[MDN Pointer Events](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events)

## 跨设备保存与同步

建议拆分保存和分析：画完 → 先可靠保存原图并返回作品编号 → 后台分析 → 家长看到处理状态 → 完成后读取结果。失败可重试分析，不要求孩子重新画。

新增持久化任务状态与重试记录，复用现有 submissionKey 幂等设计。前台先保留轮询/聚焦刷新；有真实需求再接实时连接。后台任务应在服务重启后恢复，不能只保存在内存。

离线草稿用 IndexedDB 按账号隔离，笔画结束后节流保存并在页面隐藏前尽力落盘。界面分别提示“已保存在这台设备”“等待上传”“已同步”。恢复联网且应用打开时重试；不依赖所有系统都支持后台同步。浏览器本地存储不能作为唯一永久备份，需处理空间不足和数据清理。

## 安装、配对与通知

儿童端提供“Luma 创作”图标，家长端提供“Luma 家庭”图标。可由同一仓库生成角色入口；正式安装阶段建议使用独立 origin，例如 draw.example.com / family.example.com，两边 /api 反代到同一服务。隔离登录存储和缓存，避免同设备两种角色互相覆盖；权限仍由服务端检查。

家长先在手机建家庭，平板通过短时有效、一次性的配对码/二维码加入。二维码不能携带家长登录令牌；平板只能获得儿童权限。儿童设备不能通过切换页面直接获得家长报告。

首次完成核心操作后再提示添加桌面。缓存公共外壳与素材；报告接口、令牌和跨账号原图不能被通用离线缓存误存。更新应用应在画作保存后提示重启，避免绘画中刷新。

通知只给家长，内容如“有一幅新作品”或“本周摘要已更新”，不在锁屏展示敏感解读。iOS/iPadOS 的 Web Push 需要支持的系统、主屏幕 Web App 和用户授权，普通浏览器标签页不能按同样能力承诺。通知放第二阶段，不能作为家长获取作品的唯一途径。[WebKit Web Push 说明](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

## 实施顺序与验收

| 阶段 | 交付 | 验收 |
| --- | --- | --- |
| P0 家长手机 | 移除横屏拦截、底部导航、竖屏详情与报告 | 360/390/430 CSS px 下无横向溢出，单手可查看作品与摘要 |
| P1 平板创作 | 工具栏、笔/触控模式、坐标与旋转、持久草稿 | iPad 与至少一台目标安卓平板，连续绘画/切后台/旋转后作品仍完整 |
| P2 保存同步与 PWA | 先存后分析、任务状态、离线队列、桌面入口、配对 | 断网重连仅生成一份作品，家长看到真实状态，双角色安装互不串号 |
| P3 使用反馈后决定 | 家长通知、性能优化、评估原生/小程序 | 依据安装完成率、草稿丢失率、误触率、同步延迟和家庭回访情况决定 |

具体工期在设备清单和页面原型确认后估算；P0 可以独立先交付。目标设备至少包含 iPad Safari/桌面安装模式、安卓平板目标浏览器、iPhone Safari、安卓手机浏览器，并单独检查微信内打开的基本查看流程。

## 何时考虑原生或小程序

如果真实平板测试显示笔画延迟、防误触、后台保存或系统集成达不到核心要求，再优先升级儿童画布为原生。仅套一层 WebView 不会自动解决这些绘画问题。

如果家庭主要通过微信回访，且 PWA 安装转化低，可评估家长轻量小程序复用后端；那是后续分发选择，需要独立设计与平台验证，不与本轮双端改造同时铺开。

推荐首先实施 P0：它能直接解决目前家长手机必须横屏的问题，并为后续安装和通知提供合适的手机页面。
