# 知识库分层与调度

> 当前实现，2026-09-08。数据位于 `knowledge/`，运行期调度见 `server/src/services/kbDispatcher.js`；评分语义见 [RAG 设计](RAG设计.md)。

## 数据层

| 层 | 文件 / 数量 | 职责 |
| --- | --- | --- |
| L1 实证层 | entries.jsonl，26 条 | 策展的研究关联条目；仍须过特征、年龄与评分门控 |
| L2 体系层 | entries.jsonl，3 条 | 经典体系条目，较低权重与组证据上限 |
| L3 经验层 | entries.jsonl，2 条 | 需同情绪组已有 L1 命中才保留 |
| L4 约束 | constraints.json | 年龄、冲突登记、红线等配置 |

层名是知识管理分类，不代表 Luma 已获得相应的实证有效性验证。strength/reliability 是策展参数，不是为该用户测得的概率。

## 运行顺序

1. 逐条检查 featureMatch；条件全部满足才命中。
2. 数字画板丢弃依赖 composition.pressure / erasureMarksMin 的条目，并记录原因。
3. 对 ageMods.affectedEntries 指定条目，根据年龄段将所涉及维度的模型 confidence 乘以 multiplier，再过 0.5 门控：4–7 岁 ×0.5，8–12 岁 ×0.8。这里是保留/丢弃，不是把权重减半。
4. L3 仅保留同情绪组有 L1 命中的项。
5. CONFLICT-01 两项共现时移除 weather 簇；CONFLICT-02 对擦改条目要求线条簇支撑；CONFLICT-03 的限制已体现在条目数据中。
6. 按 strength × reliability 排序，将命中、冲突、丢弃交给评分和审计。

年龄来自家长填写的 birth_date；正式报告忽略客户端 childAge，未填生日不推测年龄。

## 校验与运行配置

`node knowledge/scripts/validate.mjs` 检查 ID 唯一、来源、匹配字段、权重范围、层级范围与强度上限等。L1/L2/L3 strength 上限分别为 0.6 / 0.2 / 0.2，由知识校验执行；调度器不在每次匹配时自动重写所有条目的强度。

`dispatch.config.json` 同时包含实际读取参数和设计说明。运行中 app.js 读取 L2 的 groupEvidenceCap；score.js 对全来自 L2/L3 的组把 E 限制到该值（默认 0.6）。E 经启发式映射后才成为 S，不能简单由 E < 0.7 得出“一律信息不足”。其他 policy/索引/decision 字段不是通用规则解释器，完整生效逻辑以代码为准。

知识文件在启动时读取，不热更新。新增条目或修改规则后运行校验和后端测试并重启服务；旧报告保持原有知识版本和结果，需要时由家长重新生成。

## 审计

保存 knowledgeVersion、matchedEntryIds、conflicts、dropped 与 reason。知识版本当前由条目数量及约束版本组合，不是内容级加密摘要；若同数量替换条目而不升级版本，单凭此字符串不能唯一识别知识内容，应同步维护版本与 Git 变更记录。

周期摘要另有来源哈希，用于源数据变动时更新汇总；它不替代单幅报告的知识版本管理。
